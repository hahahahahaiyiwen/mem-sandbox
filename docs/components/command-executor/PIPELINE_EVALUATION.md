# Command Composition Usability Pilot

**Status:** Directional design evidence

## Question

Would rejecting pipelines and multiline shell input make the MemSandbox command executor
unnatural for coding agents, causing avoidable repair turns or making common tasks
impractical?

This pilot evaluates first-plan command generation. It informs the command language and
tool-surface roadmap, but it is not a production benchmark.

## Method

One plan was generated by each of three model families:

- GPT-5.6 Sol
- Claude Sonnet 5
- Gemini 3.7 Flash

Each model received the same 12 representative tasks under three conditions:

1. **Generic shell:** the model was asked to solve the task in a normal Linux shell.
2. **Constrained executor:** the model was told the exact eight-command MemSandbox
   profile and its supported grammar.
3. **Complete MemSandbox surface:** the model could choose among constrained `execute`,
   `read_file`, `write_file`, and `apply_patch`.

The corpus covered:

| Tasks | Category | Representative work |
|---|---|---|
| T1-T6 | Basic workspace manipulation | Create directories and files, change cwd, read, list, and remove |
| T7 | Recursive discovery and counting | Count Python files in a tree |
| T8 | Recursive text search | Return the first matching TODO/FIXME lines |
| T9 | File metadata aggregation | Return the largest files |
| T10 | Structured data extraction | Read one value from JSON |
| T11 | Log aggregation | Return the most frequent error messages |
| T12 | Multiline file creation | Create a file with exact multiline content |

The pilot counted generated syntax and commands, whether the task was expressible, and
the number of proposed tool calls. It did not execute the generated plans.

## Results

### Generic-shell behavior

| Metric | Result |
|---|---:|
| Plans containing a pipeline | 12/36 (33%) |
| Analysis plans T7-T11 containing a pipeline | 12/15 (80%) |
| T12 plans using multiline heredoc input | 3/3 (100%) |
| First plans compatible with the eight-command MVP | 10/36 (28%) |
| Basic T1-T6 plans compatible with the MVP | 10/18 (56%) |

The models naturally used `find`, `grep`, `head`, `sort`, `uniq`, `wc`, `jq`,
`python3`, and `printf`, plus common options such as `ls -la`. Pipelines were therefore
only one source of incompatibility. Adding `|` without adding useful producers,
transformers, and consumers would not make these plans executable.

### Explicit constrained-executor behavior

All three model families classified T1-T6 and T12 as expressible and T7-T11 as
inexpressible. The resulting semantic coverage was 7/12 tasks per model, or 21/36 plans
(58%).

For the 21 expressible plans:

- all models stayed within the declared command and grammar surface;
- two model families usually combined the work into one `execute` call with `&&`;
- one model family preferred multiple calls;
- the mean proposed call count was 1.67 per task.

Clear capability instructions prevented pipeline and heredoc use for supported tasks.
The absence of multiline command input did not itself force one model turn per simple
command because `;` and `&&` provided bounded sequencing.

### Complete MemSandbox tool-surface behavior

The robustly expressible set became T1-T6, T10, and T12: 8/12 tasks per model, or 24/36
plans (67%). The mean proposed call count for those plans was 1.5.

All three models used one `write_file` call for T12 instead of constructing a heredoc.
This is strong evidence that exact multiline file creation belongs in the file API rather
than requiring shell-compatible multiline syntax.

`read_file` plus model reasoning made the bounded JSON task practical. Models disagreed
about the log-aggregation task: loading a small complete log can work, but it is not a
scalable sandbox-side computation strategy. Recursive counting, search, and file-size
ranking remained unavailable.

## Interpretation

### Pipelines are natural for data reduction

Models strongly associate recursive discovery, filtering, counting, grouping, and ranking
with shell pipelines. Rejecting pipelines matters most for these tasks, not for basic file
manipulation.

### Pipeline syntax alone has little value in the first command wave

The eight MVP commands do not include the utilities that made the generated pipelines
useful. Implementing `|` now would mostly permit compositions such as `cat | cat`; it
would not solve T7-T11.

### Accurate capability descriptions are part of correctness

When the model received the exact constrained profile, it stopped assuming broad Unix
behavior for the expressible tasks. Adapters must generate descriptions from registered
command metadata and must not advertise the executor as a generic Bash or POSIX shell.

This matches surrounding ecosystem expectations:

- OpenAI documents sandbox agents as Unix-like environments with shell commands and
  scripts: [OpenAI sandbox agents](https://developers.openai.com/api/docs/guides/agents/sandboxes).
- Anthropic's built-in Bash tool requires the application to own a persistent Bash
  process and demonstrates `ls -la`, heredocs, package installation, and script
  execution: [Anthropic Bash tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool).
- Deep Agents exposes structured filesystem tools including `glob` and `grep`, while
  shell execution is available only on shell-capable backends:
  [Deep Agents backends](https://docs.langchain.com/oss/python/deepagents/backends).

Using a standard shell capability for the constrained interpreter would therefore create
the wrong model prior.

### Structured file tools reduce script pressure

`write_file` eliminates the primary heredoc use case. `read_file` and `apply_patch`
similarly avoid shell encoding and quoting for common file workflows. They do not replace
sandbox-side discovery and aggregation because returning whole trees or logs increases
tokens, latency, and truncation risk.

## Recommendation

Keep issue #4 focused on the approved deterministic eight-command executor, but make its
internal command contract ready for bounded sequential pipelines:

- give command requests an explicit stdin value, empty in the MVP;
- declare in command metadata whether stdin is accepted;
- keep stage stdout separately available from aggregate execution output;
- represent simple commands as immutable stages so a later pipeline node does not require
  rewriting handlers;
- continue recognizing `|` as an explicit unsupported token until the composition profile
  is implemented.

Before the first framework adapter, extend the planned complete command profile with:

- sequential in-memory `|`, with no host process or concurrent stage execution;
- `head`, `tail`, `grep`, `find`, `wc`, `sort`, and `uniq`;
- bounded structured search or file-info APIs when command output would otherwise require
  returning large trees or files to the model.

Do not add heredocs or arbitrary shell scripts merely for file creation. Keep
`write_file` and `apply_patch` as the preferred exact-content operations. If multiline
command sequencing is later supported, treat newlines as constrained plan separators,
not as permission to emulate Bash.

## Required follow-up evaluation

After the parser and first-wave commands exist, run an executable evaluation against the
real tool loop and record:

- first-attempt parser and registry acceptance;
- task completion rather than declared expressibility;
- repair turns after `CommandSyntaxUnsupported` and command-not-found results;
- tool-call count;
- input and output tokens;
- latency;
- output bytes and truncation;
- behavior on realistic repository trees and large logs.

Use multiple samples per model. The current pilot used coding-agent wrappers rather than
raw provider APIs, one sample per condition, synthetic tasks, and no execution, so its
percentages are directional rather than statistically stable.
